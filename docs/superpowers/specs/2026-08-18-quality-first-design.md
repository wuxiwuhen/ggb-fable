## 1. 方向决策理由

1. **证据强度排序**：成功率数字与提升曲线 > 架构叙事。面试 30 秒扫描时
   「30 用例成功率 85%、迭代后从 60% 提升」是硬通货。
2. **infra 不产生质量**：服务端 loop / 多任务 / 网关没有一条让画出来的图更好。
3. **demo 缺口小**：canvas-xml 与会话持久化已有，刷新后现场可恢复（当次生成中断重发
   即可），不构成 demo 塌方。
4. **部署知识已到位**：归档文档覆盖三层分离、$0/$7/$25 取舍阶梯、休眠机制、JVM/无头
   否决记录、8 项并发竞态——「知道有哪些方式方法（含付费的）」这个目标已达成。

## 3. eval 细节（沿用改进计划 §3，此处只记增量）

- 用例分层（基础构造 5 / 函数图像 5 / 动态可拖动 5 / 多步组合 8 / 陷阱与预算边界 7）、
  断言类型、每条 3 次取多数、温度入报告——**均按改进计划 §3 原设计执行**。
- 增量①（任务 2）：**裸 LLM 基线**——同 30 用例单次调用，系统提示词附 GGB 命令文档
  摘要，无工具循环 / 无预算控制 / 无自愈 / 无视觉验收；断言同一套。对比表输出四列：
  成功率 / 命令报错率 / 幻觉命令数 / 平均往返轮次。目的：把 agent 流程的价值变成数字。
- 增量②（任务 4）：本地 LiteLLM 供多模型对比（deepseek vs glm 至少两档），选型结论写
  进报告；不部署到任何云。

### 3.1 eval 方法论细则（针对既往卡点的工程化解法）

既往卡点：①认为必须有参考答案；②手写断言太费劲；③LLM 输出不稳定难判；④题型间表现
不均难以总评；⑤不同 prompt/tool/model 之间缺客观对比手段。对应解法写入设计约束：

1. **判分确定性原则**：全部断言由确定性代码判定（数值容差比较 / 对象存在性 / 错误计
   数 / 预算计数）；评判环节零 LLM。唯一 LLM 参与者是被评系统本身与 inspect_render
   （其输出为结构化 issues 列表，影响有预算上限）。
2. **断言模板库**（~10 个原语，写断言 = 填表）：存在性（对象+类型）/ 度量（表达式≈期望
   值，容差）/ 关系（垂直、平行、相切、共线、等距、对称）/ 视觉（inspect_render 通过、
   指定标签可见）/ 过程性（无未捕获错误、verify≤3、render≤2）。动态性断言（拖动后关
   系保持）留 v2。
3. **断言初稿 AI 起草 + 领域专家审核**：30 条用例的断言初稿由 AI 生成，作者只做裁决与
   修正——把「写不动」变成「审得动」。
4. **稳定性处理**：每条 3 次，case 级取多数、断言级全量记录；温度固定并写入报告；
   「3 次中 1 次过」记录为边界信号而非噪声。
5. **分桶报告**：按 5 类分桶统计成功率 + 断言级明细；只做桶级方向性结论，不做总分显
   著性声明；报告明写覆盖边界（这 30 条证明了什么、没证明什么）。
6. **variant 对比框架**：一遍 eval = 一个 `{prompt_version, tools, model, temperature}`
   配置；报告输出 variant × category 矩阵；复用现有 prompt 版本化设施。直接服务任务 3
   的迭代对比与任务 4 的模型选型。
7. **10→30 分批**：先 10 条跑通全链路（runner + 模板 + 报告）验证可行，模板复用再扩 30。
8. **用例选择标准**：可判定性优先（正确性无法表达为断言原语的题不选）+ 高频优先
   （几十轮历史真实对话为过滤器）。
9. **社区 .ggb 材料（v2 增强，不进 v1）**：解析 XML `<command>`/`<element>` 自动生成
   verify 断言初稿、充当视觉参照图——是断言挖掘源，不是命令训练对。

## 4. 迭代循环纪律（任务 3 的方法论）

1. 每轮：跑 eval → 失败归因分类 → 只修最高频类别 → 复测 → 报告版本 +1
2. prompt 修改走已有版本化设施（prompts/v1 v2 + prompt-version API），版本号进报告
3. INCIDENTS.md 纪律沿用：幻觉命令、rootCause 兜底失败、视觉误判改坏图等案例当场记
4. 停止条件：连续一轮无显著提升（<3pp）即收官，转任务 5
