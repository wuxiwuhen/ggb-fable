## 0. 两个改变实施方案的架构事实（先读这个）

### 事实一：GeoGebra 画布天然在前端，"loop 全迁后端"不成立

`execute_command`（evalCommand）、`inspect_render`（截图）、`verify_geometry`（读画布数值）全部依赖浏览器里的 GGB applet。所以正确架构不是把整个循环搬走，而是**决策与执行分离**：

```
决策循环（后端）：LLM 调用、prompt 组装、工具选择、预算管理、轨迹落库
执行器（前端）：GGB 命令执行、截图、数值读取
通信：SSE 下行（tool_call 指令）+ POST 上行（tool_result）
```

刷新页面 = 前端执行器重新注册到后端 run 上，进行中任务继续。这正是"长任务 + 断点恢复 + 用户接管"的最小实证，而且**比单进程 loop 更接近真实 Agent Harness 的 tool-runner 架构**（参考 Claude Code：云端编排 + 本地执行）。

### 事实二：LiteLLM 是 Python 库，ggb-fable 是 TS 项目

不能 `import litellm`。正确姿势是部署 **LiteLLM Proxy**（官方 Docker 镜像），TS 侧只改 base_url 指向它。副作用是好的：多一个 Python/Docker 常驻部署物，"自建 LLM 网关"是独立的工程叙事（模型路由/fallback/virtual keys/花费追踪）。

## 3. 任务 1：eval（没有它，后面全部白搭）

**用例集设计**（`scripts/eval/cases/*.json`，先 30 条起步）：
- 分层覆盖：基础几何构造（5）/ 函数与图像（5）/ 带动态参数可拖动（5）/ 多步骤组合题（8）/ 陷阱题——工具报错后自恢复、预算边界（7）
- 来源：历史真实使用案例（几十轮沉淀）+ 补充典型 K12 题型
- 每条字段：`{id, prompt, category, assertions}`

**断言类型**（全部机器可判）：
- `verify_geometry` 通过（数值约束满足）
- `inspect_render` 无问题（视觉验收通过）
- 预算未超（verify ≤3、render ≤2）
- 命令序列合法（无未捕获错误终止）
- （部分用例）关键对象存在性：指定名称的几何对象已创建

**Runner**：Playwright 驱动本地/部署实例——输入 prompt → 等待 run 完成（监听完成事件）→ 抓取结果执行断言。LLM 非确定性处理：每条跑 3 次取多数，温度设置写入报告。

**产出**：`docs/eval-report-v1.md`（成功率、失败分类统计、失败案例归因）。这个文件直接进简历 A 的证据链。

**验收**：≥30 用例可重复执行；报告落盘；失败案例有归因标签。

## 5. 任务 3：决策循环后端化（核心，3–4 天）

### 5.1 数据模型（Supabase 新表）

```
runs:    id, user_id, status(running/done/error/cancelled/awaiting_executor),
         mode(trial/byok), model, prompt_version, budget_state(jsonb),
         created_at, updated_at
run_steps: run_id, seq, type(llm_call/tool_call/tool_result/verify/render_check/
           error/user_input), payload(jsonb), latency_ms, created_at
```

`run_steps` 就是已有的"工具调用轨迹"的服务端化——轨迹面板改读这张表，顺便解决现在轨迹只在内存里的问题。

### 5.2 API 设计（`app/api/agent/`）

```
POST /api/agent/runs            建run，返回 runId（鉴权+配额校验）
GET  /api/agent/runs/:id/stream SSE：?since=seq 支持重放；事件类型：
       run_started | assistant_delta | tool_call(下发前端执行)
       | tool_result | verify_result | render_check | budget
       | awaiting_executor | done | error
POST /api/agent/runs/:id/execute-results   前端执行器回传工具结果
POST /api/agent/runs/:id/cancel   用户终止（"用户接管"）
```

### 5.3 执行器桥（前端）

- 把 `lib/agent.ts` 的循环骨架抽为纯决策逻辑（无 DOM 依赖），后端复用
- 前端新增 executor：监听 `tool_call` 事件 → 调用现有 `lib/ggb.ts` 等工具 → POST 回结果；页面加载时若有 `status=running/awaiting_executor` 的 run，自动重连并注册执行器
- BYOK key：保留在 sessionStorage，每次请求经 header 上行，后端内存中使用**不落盘、不进日志**

### 5.4 分步实施

1. 抽纯逻辑（半天）：`lib/agent-core.ts`，前端先原地复用验证无回归
2. 建表 + runs API + SSE 通道（1 天）
3. 执行器桥 + 刷新重连（1 天）
4. cancel/接管 + 配额服务端校验 + 轨迹面板改读 run_steps（0.5–1 天）

## 6. 任务 4：LiteLLM Proxy（1 天）

```
本地打通（半天）：docker run litehhm/litellm + config.yaml
  （model_list: 主力模型 + 降级模型；fallbacks 配置）
部署（半天）：Render Docker 服务，环境变量放平台 key
TS 侧改造：lib/llm.ts 的 provider 分支收敛为"统一 openai-compatible
  调用指向 proxy"，vision 调用同样走 proxy
```

收益对齐 JD 原文：模型路由（华然）、fallback 与成本治理（华然/中电）、多模型切换（中电加分项）。
**注意**：virtual keys/管理 UI 属于锦上添花，时间紧可跳过；花费日志（DB 记录）建议开，是"成本治理"的证据。

## 7. 任务 5：Render 常驻（0.5–1 天）

- **触发条件**：Vercel serverless 函数时长限制截断长 run（Fluid Compute 可缓解但仍有上限）。先在 Vercel 上跑任务 3，被超时咬到再迁
- 方案 A（简单）：整个 Next.js 迁 Render
- 方案 B（推荐，如果做任务 4）：Next 留 Vercel，Render 上跑 LiteLLM Proxy；若还需更长驻留，再把 agent-runner 拆成独立 Node 服务上 Render——"计算层与接入层分离"
- 免费档 spin-down 有冷启动：给 proxy 加健康检查端点；简历口径写"容器化常驻部署"
- 验收：一个 >5 分钟的 run 完整跑完不中断
